# Multimedia opportunities: support, work discovery, and authoring

Internal supplemental analysis for Gary and the Chief of Staff, September 9, 2026. This memo adds the remaining support and authoring templates to the programwide review. It proposes no website edits or publication.

These surfaces benefit most from clear process diagrams, annotated examples, and evidence-linked owner views. Video and 3D add little to account access, settings, request lookup, or queues. The useful connection to Blender is the consultant's authoring and review workflow: an editable scene and still can become a reusable learning asset when its purpose, equivalent text, source basis, and destination are explicit.

## Scope and evidence limits

The route census contains 36 page/layout files: 33 page templates and three layouts across `/support`, `/my-work/explore`, `/areas`, `/consultant`, and `/contribute`. The lead review covers the base support, areas, contribution, and consultant navigation surfaces; this supplemental pass covers their remaining templates, shared editing/release components, support clients, and relevant contracts. The separate learning memo covers learner content and practice.

This is a local code review. It does not assert that every database-backed publication, request, program event, account, or protected screen has been visually inspected. An implemented activation check, enabled registry entry, or available button does not establish that the current deployment has its required connections. No private staff record is used as creative source material. Existing owner instructions and implemented access/publication boundaries remain authoritative; these recommendations do not create additional approval gates.

## What the current media wiring permits

The shared `ResourceInlineEditor` edits a title, type/authority/detail labels, summary, rationale, an array of plain-text body paragraphs, topics/intents/path relationships, next-action links, owner/review date, and an optional public source link. Its body control is a textarea. `EditableResourceFieldsSchema` rejects presentation markup and serialized data rather than interpreting pasted Markdown as a media block. The release payload carries body strings and links; its passthrough setting alone does not create a renderer, upload flow, caption model, or permission-aware asset delivery.

`ResourceReleaseClient` already presents distinct review dimensions, revision/history state, scope, and permitted publication/withdrawal actions. This is a useful place to connect future media evidence. It is not currently a media accessibility inspector. Review dimensions include accessibility, rights/consent, community representation, currentness, and placement; a recorded decision is not proof that a particular caption file or audio description was checked. The owner-curated publication workflow should be extended only for concrete missing asset information, without inventing an additional approval hierarchy.

The support clients and these owner/contributor templates contain no generic audio/video/3D player, recorder, or file-upload field. The public outcome link and resource source/next-step links remain links. Visual Studio is the deliberate exception: a local private preview and editable project connection. The learning memo documents separate existing course-image and audio capabilities, which should not be assumed to exist in this text-resource editor.

## Agent-count interpretation for the program map

The current `AGENTS` array has these ten entries, all with `enabled: true`: `program_orchestrator`, `ask_concierge`, `ci_guide`, `librarian`, `a11y_reviewer`, `consult_intake`, `graduation_coach`, `embed_advisor`, `content_sentinel`, and `eval_steward`. This is a code-configuration count. Registry display labels and old descriptive comments are not evidence of current live execution. Visual Studio runs through the existing orchestrator/tool path; it does not add an eleventh registry agent. Scene assembly itself does not require a language-model call.

For an honest owner diagram, distinguish five facts for each relevant capability: registered definition; enabled setting; connection/activation readiness; observed execution result; and application/publication result. An arrow can express an implemented handoff or a specifically labeled proposed handoff. It must not imply that two named support areas exchanged work merely because both appear in the registry.
